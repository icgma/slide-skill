# Roadmap: Slide Skill

## Overview

The first milestone now follows the stronger PPT Master-inspired architecture: establish a license-safe foundation, normalize source materials into reproducible project workspaces, generate slides through SVG with a spec lock and quality gate, export finalized SVGs to native editable PPTX, then add template editing and harden QA/docs/release packaging.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work.
- Decimal phases (2.1, 2.2): Urgent insertions if needed.

- [x] **Phase 1: Clean-Room Foundation** - Establish repository shape, local skill skeleton, legal boundary, and baseline verification.
- [x] **Phase 2: Source Intake And Project Workspace** - Normalize source inputs and create reproducible per-deck workspaces.
- [x] **Phase 3: SVG Design Pipeline** - Add design spec, spec lock, SVG authoring standards, and SVG quality gate.
- [x] **Phase 4: Native PPTX Export** - Convert finalized SVGs to editable PPTX with notes, backups, and validation.
- [x] **Phase 5: Template Editing Workflow** - Add safe template analysis, slide operations, content replacement, cleanup, and repack.
- [x] **Phase 6: QA, Docs, And Skill Release** - Formalize verification loops, regression tests, setup docs, and installable skill package.

## Phase Details

### Phase 1: Clean-Room Foundation

**Goal**: Establish a local project foundation that can be safely evolved while respecting Anthropic proprietary restrictions and PPT Master MIT attribution requirements.
**Depends on**: Nothing (first phase)
**Requirements**: [FND-01, FND-02, FND-03, FND-04, FND-05]
**Success Criteria** (what must be TRUE):
  1. Maintainer can identify what may and may not be copied from Anthropic references.
  2. Maintainer can identify how MIT-licensed PPT Master ideas or code may be reused.
  3. Repository has an agreed directory structure for skill docs, source tools, SVG tools, export tools, examples, and tests.
  4. A minimal local skill entrypoint exists and routes to planned guide files.
  5. A baseline verification command reports current repo health.
**Plans**: 3 plans

Plans:
- [x] 01-01: Define clean-room/MIT reuse policy, source references, and repository structure.
- [x] 01-02: Create the initial local skill skeleton and placeholder guides.
- [x] 01-03: Add baseline verification and documentation for current project state.

### Phase 2: Source Intake And Project Workspace

**Goal**: Provide the input normalization and per-deck workspace conventions needed for repeatable deck generation.
**Depends on**: Phase 1
**Requirements**: [SRC-01, SRC-02, SRC-03, SRC-04, SRC-05, SRC-06]
**Success Criteria** (what must be TRUE):
  1. Agent can create a deck workspace with stable artifact directories.
  2. Agent can normalize Markdown/pasted text, PDF, document, spreadsheet, and PPTX inputs to Markdown.
  3. Source import preserves originals or explicitly records moves/copies.
  4. Workspace validation detects missing required directories or malformed project metadata.
**Plans**: 3 plans

Plans:
- [x] 02-01: Implement workspace init, source import, and project validation.
- [x] 02-02: Implement Markdown, PDF, DOCX/HTML, spreadsheet, and PPTX source ingestion.
- [x] 02-03: Add source fixture tests and workspace regression checks.

### Phase 3: SVG Design Pipeline

**Goal**: Make SVG the primary AI-authored intermediate representation with locked design parameters and pre-export quality checks.
**Depends on**: Phase 2
**Requirements**: [SVG-01, SVG-02, SVG-03, SVG-04, SVG-05, SVG-06]
**Success Criteria** (what must be TRUE):
  1. Agent can generate a design spec and machine-readable spec lock for a deck workspace.
  2. Agent can create valid SVG pages using fixed canvas dimensions and local style rules.
  3. SVG pages use semantic top-level groups with stable IDs.
  4. SVG quality checker rejects unsupported features before finalization/export.
  5. Finalization produces export-safe SVG artifacts.
**Plans**: 3 plans

Plans:
- [x] 03-01: Define design spec/spec lock schemas and canvas format presets.
- [x] 03-02: Implement SVG authoring standards, examples, and page rhythm rules.
- [x] 03-03: Implement SVG quality checker and SVG finalization workflow.

### Phase 4: Native PPTX Export

**Goal**: Convert finalized SVG pages into editable PPTX decks with notes, backups, and package validation.
**Depends on**: Phase 3
**Requirements**: [EXP-01, EXP-02, EXP-03, EXP-04, EXP-05]
**Success Criteria** (what must be TRUE):
  1. Finalized SVG pages export to a `.pptx` deck.
  2. Exported decks contain native editable PowerPoint elements where supported.
  3. Speaker notes can be embedded or preserved.
  4. Backup artifacts include SVG snapshot deck and archived SVG sources.
  5. Export validation detects package or conversion failures.
**Plans**: 3 plans

Plans:
- [x] 04-01: Implement base SVG-to-PPTX export path and editable object mapping.
- [x] 04-02: Add notes, backup artifacts, and optional animation anchor plumbing.
- [x] 04-03: Add export validation fixtures and native-editability checks.

### Phase 5: Template Editing Workflow

**Goal**: Enable safe modification of existing template decks without corrupting slide relationships or leaving placeholders.
**Depends on**: Phase 2 and Phase 4
**Requirements**: [EDT-01, EDT-02, EDT-03, EDT-04, EDT-05]
**Success Criteria** (what must be TRUE):
  1. Agent can analyze a template deck and choose slide mappings.
  2. Toolkit can import or inspect a template deck without mutating the original.
  3. Toolkit can duplicate, delete, and reorder slides through tested commands.
  4. Edited decks pass placeholder checks and render QA.
**Plans**: 3 plans

Plans:
- [x] 05-01: Implement template import/inspection and mapping guidance.
- [x] 05-02: Implement relationship-safe slide operation commands with tests.
- [x] 05-03: Implement content replacement workflow and template editing example.

### Phase 6: QA, Docs, And Skill Release

**Goal**: Make the skill usable and trustworthy through verification workflows, docs, examples, and release packaging.
**Depends on**: Phase 4 and Phase 5
**Requirements**: [QA-01, QA-02, QA-03, QA-04, QA-05, QA-06, DOC-01, DOC-02, DOC-03, DOC-04]
**Success Criteria** (what must be TRUE):
  1. Skill requires source/content QA, SVG QA, visual QA, and at least one fix-and-verify cycle.
  2. QA artifacts are stored or referenced for examples and test runs.
  3. Setup docs cover local dependencies, optional enhancements, and Windows notes.
  4. The local skill package can be installed or copied into a Codex-compatible skills directory.
**Plans**: 3 plans

Plans:
- [x] 06-01: Formalize QA commands, issue taxonomy, and artifact conventions.
- [x] 06-02: Complete user-facing setup, recipes, troubleshooting, and dependency docs.
- [x] 06-03: Package the skill and run full milestone verification.
